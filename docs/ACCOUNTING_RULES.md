# Factory Finance — 会计与财务规则（强制）

> 本文档完整记录任务文档第 6 节已明确的财务约束，是后续所有财务业务开发的**强制规则**。
> 尚未确定的会计处理事项见第 8 节，未经架构师确认**不得擅自实现**。
> 复式记账引擎本身**计划于 Phase 3** 实现；Phase 1/2 的业务实现必须遵循本规则，避免产生 Phase 3 无法核算的历史数据。

## 1. 业务与财务分离（6.1）

系统必须区分以下数据层次，禁止混为一体：

1. 原始业务单据
2. 资金收付款流水
3. 应收应付明细
4. 核销记录
5. 会计凭证
6. 会计分录
7. 财务报表

强制事实（红线）：

| # | 规则 | 含义 |
| --- | --- | --- |
| 1 | **营业收入 ≠ 实际收款** | 收入按权责发生制在业务完成时确认；收款是资金事实，可能提前、滞后或分期 |
| 2 | **经营费用 ≠ 实际付款** | 费用确认与实际付款分离；应付款未付时不得抹掉费用，付款时不得重复计费用 |
| 3 | **股东出资 ≠ 营业收入** | 股东出资计入所有者权益（实收资本/资本公积，科目待确认），不得计入营业收入 |
| 4 | **股东借款 ≠ 所有者权益** | 股东借款是负债（往来借款），不得计入所有者权益 |
| 5 | **购买固定资产 ≠ 立即产生等额费用** | 固定资产资本化，通过折旧分期计入费用（折旧规则待架构师确认，计划于 Phase 4） |
| 6 | **账户间转账不产生收支** | 账户间划转只改变资金分布，不产生营业收入、费用或现金流净额 |

## 2. 金额规范（6.2）

1. 后端金额统一使用 **Java `BigDecimal`**。
2. 数据库人民币金额字段采用 **`DECIMAL(18,2)`**；单价、成本分摊、折旧中间计算等需要更高精度的字段**单独定义**（如 `DECIMAL(18,6)`），禁止复用金额精度。
3. **禁止使用 `float` 或 `double` 进行财务金额计算**。
4. 前后端财务金额通过**十进制字符串**传输（如 `"1850.39"`），**禁止依赖 JavaScript `Number` 进行需要精确结果的财务运算**。前端精确运算使用 BigInt 定点实现（`frontend/src/utils/decimal.ts`），输入输出均为十进制字符串。
5. **舍入方式及舍入时点必须在对应业务规则中明确**；禁止无依据地对每个中间结果提前四舍五入。默认舍入规则与各业务的舍入时点：**待架构师确认**，在确认前任何业务实现不得自行选定舍入策略。
6. 金额展示规范（千分位、两位小数、右对齐、`tabular-nums`）见 `DESIGN_SYSTEM.md`；展示层格式化不得反向影响存储与计算值。

## 3. 复式记账（6.3）

未来会计引擎（**计划于 Phase 3**）必须满足：

1. **借贷平衡**：`借方金额合计 = 贷方金额合计`，不平衡的凭证禁止过账。
2. **可追溯**：每一笔已过账业务应当可以追溯到对应原始业务单据（凭证 ↔ 单据双向关联）。
3. **已过账凭证不得直接修改或物理删除**。
4. **更正必须通过冲销、更正凭证或明确的撤销流程完成**（具体撤销流程待架构师确认）。
5. **事务一致性与幂等性**：业务单据、相关资金变动、核销和会计凭证的记账操作必须同事务提交，且重复请求不得重复记账（幂等键设计待架构师确认，单据编号唯一约束为第一道防线）。

## 4. 资金余额（6.4）

1. 资金余额必须能够通过**有效资金流水及期初余额重新计算**：
   `期末余额 = 期初余额 + Σ(有效流入) − Σ(有效流出) ± 有效调整`。
2. 允许后续设计余额缓存（提升查询性能），但**缓存不允许成为无法核对的独立数据源**：
   缓存值必须可与重算结果对账，不一致时以流水重算为准并告警。
3. 每一笔实际收付款在资金流水中**只记录一次**；核销不产生新的资金流水（见第 5 节）。

## 5. 应收账款（6.5）

未来采用三表模型（**计划于 Phase 2**）：

```text
receivable          应收单（债权）
receipt             收款单（资金流入）
receipt_allocation  核销明细（收款单 ↔ 应收单 的多对多匹配）
```

强制规则：

1. **核销明细实现收款单与应收单之间的多对多关系**：一笔收款可核销多张应收单，一张应收单可被多笔收款核销。
2. **一笔实际收款只允许记录一次资金流入**：无论核销到多少张对账单/应收单，资金流水唯一。
3. **禁止将一笔收款因为核销多个对账单而重复计入资金余额**。
4. **预收款、未分配收款、退款、坏账、折扣和冲销必须具有明确的独立业务规则**，禁止混用或用"备注"表达状态。具体规则：**待架构师确认**，计划于 Phase 2 细化。
5. 应付账款采用对称的 `payable / payment / payment_allocation` 模型，规则同上。

## 6. 编号与审计（6.6）

1. **内部主键和业务单据编号分离**：主键仅做技术标识，单据编号是业务标识。
2. **业务单据编号一旦正式生成，不得因为排序、删除其他记录或修改日期而改变**。
3. **单据编号应具有数据库唯一性约束**。
4. 多时间维度分别记录，禁止合并：
   - `biz_date`：业务发生日期
   - `pay_date`：实际收付款日期
   - `accounting_period`：会计期间
   - `created_at` / `created_by`：创建时间与操作人
   - `updated_at` / `updated_by`：最后修改时间与操作人

## 7. 实施范围（6.7）

第一版采用：

- 单工厂
- 单账套
- 人民币本位币
- 内部经营财务管理
- **权责发生制**
